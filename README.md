# DockCheck — локальная проверка оформления DOCX

DockCheck помогает студенту найти несоответствия оформления в учебной работе и
исправить их в редакторе. Сервис читает структуру DOCX, сравнивает доступные
свойства с настраиваемым профилем и показывает конкретные места, требующие
внимания.

Текущая версия — **0.1.0**, предварительный анализатор с ограниченной поддержкой
OOXML. Основной результат работы сервиса — понятный отчёт с цитатами,
расположением объектов, фактическими значениями и рекомендациями.

Документ обрабатывается в браузере, не отправляется на сервер и не изменяется.
Автоматического исправления и скачивания исправленного DOCX в этой версии нет.

Подробное устройство проекта, контракты данных и порядок расширения описаны в
[ARCHITECTURE.md](ARCHITECTURE.md).

## Для кого предназначен сервис

Основной сценарий — предварительная проверка отчёта, курсовой или другой учебной
работы перед нормоконтролем. Пользователь получает список мест для исправления
и отдельный список того, что сервису не удалось проверить.

Преподаватель или нормоконтролёр может использовать отчёт для первичного разбора
документа. Разработчик может вызывать анализатор отдельно от интерфейса через
`checkDocx(data, requirements)`.

Сервис не выдаёт заключение «готово к сдаче». Успешная проверка отдельного свойства
не подтверждает соответствие всего документа, а неизвестный результат не означает
доказанное нарушение.

## Цели текущей версии

1. **Помочь найти конкретную ошибку.** Замечание связывается с частью DOCX,
   абзацем или объектом и, когда это применимо, с точным диапазоном текста.
2. **Объяснить отличие от профиля.** В отчёте показываются факт, требование,
   источник свойства и действие для исправления в Word.
3. **Сделать ограничения заметными.** Недоступные свойства и неподдерживаемые
   конструкции сохраняются в отчёте как непроверенные области.
4. **Сохранить локальную обработку.** Для анализа не нужны загрузка на сервер,
   учётная запись, Word COM, LibreOffice или внешний API.
5. **Создать основу для расширения анализатора.** Извлечение OOXML, разрешение
   оформления, проверки и представление отчёта выделены в отдельные модули.

Текущая версия завершает основной сценарий поиска ошибки и реализует часть
расширенного разрешения оформления. Полная совместимость с Word ещё не достигнута.

## Как пользоваться

1. Откройте «Шаблон проверки» и уточните требования своей организации.
2. Выберите DOCX или перетащите его в область загрузки. Ограничение интерфейса —
   **25 × 1024 × 1024 байт**; принимаются файлы с расширением `.docx`.
3. Просмотрите сводку и подтверждённые нарушения. Фильтры позволяют выбрать
   категорию, а повторения одного правила объединены в раскрываемую группу.
4. Откройте нужное место, изучите выделение и полный контекст.
5. Нажмите «Скопировать цитату для поиска» и вставьте текст в поиск Word, Ctrl+F.
6. Проверьте раздел «Проверить вручную»: в нём находятся неизвестные результаты
   и ограничения анализа.
7. При необходимости скачайте текстовый отчёт со всеми результатами.

После изменения шаблона нужно загрузить документ повторно: настройки применяются
к следующему запуску анализа. Профиль сохраняется в `localStorage` браузера;
исходный DOCX и отчёт приложение туда не записывает.

## Что показывает замечание

Для текстового нарушения карточка содержит:

- понятное название с фактическим и ожидаемым значением;
- путь к месту: область, раздел, абзац, а для таблицы — таблицы, строки и ячейки;
- статус страницы и пояснение достоверности;
- дословную цитату с выделением проблемного диапазона;
- полный абзац в раскрываемом контексте;
- рекомендацию и раскрываемые сведения об источнике свойства и требовании.

Ошибка свойства абзаца выделяет весь абзац. Ошибка шрифта может выделять только
часть одного run: например, символы другой письменности с отличающимся шрифтом.
Одинаковые цитаты в разных местах различаются по идентификаторам и смещениям.

В полном контексте отображаются пробелы, неразрывные пробелы, табуляции и разрывы
с доступными названиями. При копировании берётся исходный диапазон без этих
обозначений, многоточий и HTML-разметки. Для доступа к буферу обмена нужны
поддержка и разрешения браузера; отказ сопровождается сообщением.

Для нетекстовых объектов и отсутствующего содержимого используется описание
расположения. Вымышленная цитата не создаётся. Ошибка распознанной подписи
связывается с абзацем самой подписи; произвольный соседний текст не считается
неправильно оформленной подписью.

## Какие проверки выполняются

| Проверка | Область и поведение |
| --- | --- |
| Семейство шрифта | Назначенный шрифт сравнивается с профилем для выбранных ролей; фактический font fallback не определяется |
| Размер шрифта | Итоговый размер текстового фрагмента сравнивается с заданным кеглем |
| Полужирный заголовок | Проверяется bold у распознанных заголовков; это отдельное правило текущей реализации |
| Выравнивание | Для основного текста при включённом требовании ожидается выравнивание по ширине |
| Абзацный отступ | Первая строка или выступ сравниваются с заданным отступом |
| Межстрочный интервал | Режим `auto` переводится в множитель и сравнивается со списком допустимых значений; `exact` и `atLeast` требуют ручной проверки |
| Формат A4 | При включённом требовании проверяются ширина и высота с учётом объявленной ориентации |
| Поля страницы | Проверяются параметры секций; альбомные поля и внутреннее/внешнее поле зеркального режима не сравниваются уверенно с портретным профилем |
| Подписи таблиц и рисунков | Проверяется распознанная соседняя подпись вида «Таблица N – Наименование» или «Рисунок N – Наименование»; отсутствие подходящей подписи даёт unknown |
| PAGE в нижнем колонтитуле | Проверяется собственный абзац поля и его центрирование в определённых для секции вариантах колонтитула |
| Обязательные разделы | Ищется совпадение текста; структурная роль остаётся unknown даже при совпадении |
| Ограничения | Отдельные unknown для пропущенных конструкций, видимых номеров списков и фактической пагинации |

**Извлечение свойства само по себе не является проверкой соответствия.** Например,
цвет, границы таблиц и высота строки могут присутствовать в модели, но правил
сравнения этих свойств с нормативным профилем сейчас нет.

## Настраиваемый профиль

В интерфейсе доступны семейство и размер шрифта, допустимые межстрочные интервалы,
абзацный отступ, выравнивание по ширине, поля вертикальной страницы, переключатели
A4 и нумерации, список обязательных разделов и роли для проверки шрифта/кегля.

Начальные значения:

| Параметр | Значение |
| --- | --- |
| Шрифт / кегль | Times New Roman / 14 пт |
| Межстрочные интервалы | 1 или 1,5 |
| Первая строка | 12,5 мм |
| Поля сверху / справа / снизу / слева | 20 / 10 / 20 / 30 мм |
| A4, выравнивание по ширине, PAGE | Включены |
| Роли шрифта и кегля | Только основной текст |
| Разделы | ВВЕДЕНИЕ; ЗАКЛЮЧЕНИЕ; СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ |

Можно включить тот же шрифт и кегль для заголовков, списков, таблиц, подписей,
сносок, колонтитулов и текстовых блоков. Если роль не включена, результат этих
правил остаётся unknown; извлечённый факт при этом сохраняется.

Профиль унаследован от прежней реализации. Его значения и ссылки на СТУ СФУ
7.5-07-2021 **не являются независимо проверенной копией стандарта**. Пользователь
должен сопоставить шаблон со своими требованиями. Текущие результаты обозначают
сравнение с профилем, а не сертификацию по СТУ.

В API сохранён параметр `requireContentsOverPages: 24`, но правило необходимости
содержания по числу страниц не выполняется: надёжного количества страниц нет.

Технические допуски шрифта, отступа и A4 — 0,01 пт и 0,02 мм; для множителя
интервала — 1/240 строки с малой поправкой на арифметику JavaScript. Это допуски
сравнения, а не нормативное разрешение отклонений. **Известная несогласованность:**
предикат полей секций сейчас использует 0,7 мм, хотя в метаданных результата
записано 0,02 мм. Это ограничение текущего снимка, требующее отдельного исправления.

## Страницы и достоверность

DOCX анализируется как поток XML без движка вёрстки. Точных страниц Word текущая
версия не вычисляет.

| Статус | Что видит пользователь |
| --- | --- |
| `saved` | «Страница ≈ N — по сохранённой разметке DOCX; в Word может отличаться» |
| `unknown` | «Страница не определена» и причина |
| `confirmed` | Предусмотрен контрактом для совместимой вёрстки; текущий анализатор никогда его не выдаёт |

Ориентир используется только между двумя `lastRenderedPageBreak`. До первого и
после последнего маркера страница неизвестна. Пересечение границы всем абзацем
не даёт одного номера всему абзацу; для фрагментов учитывается позиция границы.

При явном разрыве страницы, действующем `pageBreakBefore`, нескольких секциях или
зарегистрированной неподдерживаемой области ориентиры консервативно отключаются.
Разные виды разрывов не суммируются. Сохранённые маркеры могут быть устаревшими.

Физическая страница отделена от печатного номера. Формат и старт секции извлекаются,
но напечатанный номер не вычисляется. Колонтитул связывается с разделами и
вариантами использования, поскольку может повторяться на нескольких страницах.
Количество страниц и необходимость содержания по сохранённым данным не доказываются.

## Отчёт и экспорт

Внутренние статусы — `pass`, `fail`, `unknown`, `not_applicable`. Степень важности
`severity` хранится отдельно. В текущих правилах используется `warning`; это не
превращает fail в unknown. `not_applicable` предусмотрен моделью, но отдельные
правила сейчас преимущественно пропускаются или дают unknown.

Сводка считает все результаты до группировки. Процент пройденных проверок зависит
от состава правил и документа и не является оценкой качества работы.

Текстовый экспорт включает все результаты, включая успешные и неизвестные:
статус, правило, путь, структурированное расположение, страницу с достоверностью,
цитату и полный абзац при наличии, факт, требование, источник, область,
метаданные допуска, объяснение и рекомендацию. Имя файла отчёта образуется из
имени загруженного документа. Экспорта исправленного DOCX нет.

## Ограничения текущей версии

- Нет вёрстки, точной пагинации, проверки фактического положения объектов,
  установленных шрифтов и font fallback.
- Поддержка Transitional OOXML частичная; Strict OOXML не поддерживается.
  Проверки упаковки не являются полным валидатором OPC и всех схем OOXML.
- Не покрыты все правила выбора шрифта, themeFontLang, hint, bidi и сложные
  письменности. Размер Arab/Hebr помечается unsupported до отдельного разрешения
  szCs. Округление RGB после HSL может отличаться от Word.
- Условное оформление таблиц с vMerge и старым hMerge остаётся unsupported.
  Не завершены наследование геометрии, конфликты границ и все сочетания свойств.
- Видимые номера списков и состояние счётчиков при перезапуске не вычисляются.
  Не все связи уровней с paragraph styles поддержаны.
- PAGE за пределами одного абзаца, вложенные/вычисляемые поля, переключатели и
  фактическое отображение номера требуют ручной проверки. Одиночный instrText
  не подтверждает корректное поле PAGE.
- Правки ins/del/move не принимаются автоматически: соответствующий текст
  исключается из анализируемой проекции с явной непроверенной областью. Изменённые
  свойства и строки таблиц обрабатываются консервативно. Полная модель всех видов
  tracked changes не реализована.
- Неизвестные конструкции, altChunk, VML-оболочка и AlternateContent фиксируются
  как непроверенные области. Доступный текстовый блок анализируется отдельно;
  Choice/Fallback не учитываются дважды.
- Роли определяются эвристически по стилям, outline level и контексту. Номер в
  начале строки не доказывает роль заголовка; найденный текст раздела не доказывает
  его структурную роль.
- Все комплектные фикстуры синтетические. Нет набора файлов, сохранённых настоящим
  редактором с независимо известными настройками; открытие в Word/LibreOffice не
  проверено. Это остаётся отдельной задачей качества.

## Запуск и сборка

Нужны Node.js и npm, совместимые с зависимостями из `package-lock.json`.

```sh
npm ci
npm run dev
```

Vite настроен на порт **4173** и при занятости может выбрать следующий. Команда
`dev` слушает `0.0.0.0`; доступность по сети зависит от окружения. Данные документов
по-прежнему анализируются в клиентском коде.

```sh
npm test
npm run build
```

`build` сначала выполняет `tsc --noEmit`, затем создаёт статические файлы в `dist/`.
Их можно размещать на статическом хостинге. Серверный анализатор, база данных,
авторизация и API-ключи текущей версии не требуются. Clipboard API зависит от
поддержки браузера, разрешений и контекста безопасности страницы.

## Проверка качества

Текущий набор — **56 автоматических тестов** Vitest. Проверяются каскады,
темы, таблицы, списки, секции, PAGE, повторяющиеся цитаты, Unicode, диапазоны,
страницы, правки, ошибки XML/OPC, области правил, группировка и экспорт.

В `tests/fixtures` находятся комплектные синтетические DOCX:

| Файл | Назначение |
| --- | --- |
| `correct.docx` | Оформление, совпадающее с проверяемой частью профиля |
| `incorrect.docx` | Отличающиеся шрифт и кегль |
| `partial.docx` | Неопределённость из-за отсутствующего стиля |
| `search.docx` | Повторные цитаты, длинный контекст, emoji, сохранённые границы, вложенные таблицы |
| `textbox.docx` | Отдельный текстовый блок внутри VML с явным ограничением оболочки |

Генераторы:

```sh
node tests/fixtures/generate.mjs
node tests/fixtures/generate-search.mjs
```

Сценарий `scripts/check-ui.mjs` проверяет в Chromium загрузку пяти фикстур,
выделение и контекст, копирование, страницы, группы, фильтры, экспорт, экран
390 px, выбор ролей и клавиатуру в настройках. Он также проверяет отсутствие
ошибок JavaScript и запросов передачи документа. Playwright не входит в
зависимости проекта; для этого сценария нужен доступный пакет и Chromium.

При работающем Vite и доступном через Node Playwright:

```sh
DOCKCHECK_URL=http://localhost:4173 node scripts/check-ui.mjs
```

Если пакет установлен отдельно:

```sh
PLAYWRIGHT_MODULE=/absolute/path/to/playwright/index.mjs \
DOCKCHECK_URL=http://localhost:4173 node scripts/check-ui.mjs
```

Сценарий ожидает hostname `localhost`. Артефакты его запуска записываются в `/tmp`:
`dockcheck-*-v2.png`, `dockcheck-search-mobile.png`, `dockcheck-report.txt`.
Браузерная проверка не заменяет открытие DOCX в настоящем редакторе.

## Направления развития

Ближайшие цели — расширить проверенный набор документов реальных редакторов,
