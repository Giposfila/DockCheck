# Шаблон нормативных требований DockCheck

Редакция каталога: `stu-2021.2`. Основание: 15 замечаний в `REQUIREMENTS_AUDIT.md`.
Машиночитаемый контракт находится в `src/requirements/schema.ts`, профиль работы —
в `profile.ts`. Этот документ объясняет заполнение контракта и критерий полноты.

Одно правило описывает одну обязанность, запрет, рекомендацию или разрешение.
Право выбрать вариант и ограничения выбранного варианта записываются отдельно.
Например, рукописная вставка разрешена, а чёрная паста обязательна после её выбора.
Нормы СТУ, локальные нормы и сведения пользователя имеют разное происхождение.

| Часть карточки | Что записывать |
| --- | --- |
| Идентификация | Постоянный `id`, название, описание, версия каталога |
| Нормативный источник | Редакция, пункт, страница PDF, приложение, форма |
| Точный источник | `source.locators`: id атома, SHA-256 документа и фрагмента, первая/последняя строка |
| Статус источника | `appendixStatus`: обязательное, рекомендуемое, справочное приложение; отдельно `contentKind`: норма, пример, определение, справочник |
| Нормативная сила | `mandatory`, `prohibition`, `recommendation`, `permission` |
| Применимость | `when`: контекст работы или выбранного объекта; неизвестные факты сохраняют `unknown` |
| Объекты | `target`, `selector`: тип, роль и область выбранного объекта |
| Проверка | `property`, `assertion`: значение, множество, диапазон, минимум/максимум либо типизированная связь |
| Исключения | `exceptions`; подтверждённое исключение имеет приоритет над общим правилом |
| Варианты | `alternatives` и условия выбранного варианта, например `numbering.tables` |
| Предпосылки | `dependsOn`: непроверенные предпосылки не позволяют подтвердить зависимый результат |
| Доказательства | `evidence`: OOXML, структура, счётчики, вёрстка, геометрия, язык, эксперт, внешний документ/артефакт |
| Внешние нормы | `externalDependencies`: конкретное обозначение и редакция; наличие ссылки не означает проверки полного ГОСТа |
| Результат | Объяснение, рекомендация, применимость, источник факта, расположение, исходная цитата и статус |

В `RelationSpec` операнды задают коллекцию, свойство, область и связь с объектом
(`self`, `owner`, `target`, `members`). Допустимы только перечисленные в схеме
валидаторы. `same-property` сравнивает свойства явно связанных подтверждённых
объектов. `membership` проверяет принадлежность значения множеству связанного
объекта. Валидаторы геометрии, последовательности и экспертной оценки требуют
своих адаптеров доказательств; само имя валидатора не подтверждает соответствие.
`relations.ts` возвращает `unknown`, когда необходимых объектов или реализации нет.

Условия поддерживают `eq`, `in`, `lt`, `lte`, `gt`, `gte`, `not`, `all`, `any`,
`every`, `some`. Порог содержания выражается непосредственно как
`confirmedPageCount <= 24`, с рекомендательной модальностью. Ориентировочное
число страниц не подставляется в этот факт. Для коллекций проверяется каждый
соответствующий объект; неизвестная коллекция отличается от подтверждённо пустой.

`FACT_REGISTRY` указывает ожидаемый источник факта. Это контракт поставщика,
а не заявление, что факт уже извлекается. Неизвестное содержимое, неподтверждённая
структурная роль и отсутствующее доказательство не заменяются значением `false`.
Наличие искомого элемента не может быть условием требования его наличия.

## Контекст комплекта

Профиль независимо задаёт `medium` (`paper`/`electronic`) и `execution`
(`printed`/`handwritten`). Старое `medium: handwritten` читается как способ
исполнения с неизвестным носителем. Указание профиля — сведения пользователя,
а не доказательство оформления DOCX.

Каждый `artifactManifest` содержит id, вид, имя, наличие и источник. Дополнительно
задаются носитель, способ исполнения, `parentId`, `pageCountScope` и `sheets`.
У листа собственные id, формат, форма основной надписи, вид чертежа, система
документации, носитель, исполнение и признак первого листа. Ссылки на отсутствующий
родительский артефакт и циклы запрещены.

Основные надписи проверяются в контексте листа, включая графический материал БР
без рамки в текстовой части. Наличие графы зависит от формы надписи. Требования
к массе детали не переносятся на текстовый лист. Складывание выбирается по формату
чертежа или плаката. При отсутствии листовых сведений результат неизвестен.

Контекст формулы, таблицы, рисунка, библиографической ссылки и приложения
передаётся для конкретного объекта. Формула в таблице исключается из общего
правила нумерации. Общая/разные единицы таблицы и продолжение таблицы различаются.
Отдельный документ-приложение отличается от продолжения исходного документа.

## Содержание, формы и справочники

Наличие компонентов реферата и введения сохраняется для экспертного рассмотрения.
Возможный состав заключения остаётся разрешением. Состав основной части зависит
от темы и вида работы; профиль не требует все перечисленные разновидности материала
у любой работы. Качественная оценка хранится отдельно от наличия компонента.

`TITLE_BLOCKS` описывает постоянные надписи, сведения о работе и подписантов.
Подпись, дата, инициалы, фамилия, должность, степень, группа и номер зачётной книжки
выделяются по применимой форме. Консультанты — повторяющиеся блоки, связанные
с разделами. Рецензент — необязательный блок. Гриф утверждения не добавляется
к формам И, К, М, Н по аналогии с другими формами.

`DOCUMENT_CODES`, `SCHEME_KINDS`, `SCHEME_TYPES` сохраняют справочные значения
приложения Х. Они помогают описывать обозначения, но не требуют включать в работу
все виды документов. `VISUAL_REFERENCES` привязывает геометрию форм и порядок
складывания к страницам оригинального PDF с его SHA-256. Массив длин не заменяет
геометрию внутренних граф. Без соответствующего адаптера сравнение остаётся
ручным. Темы, номера страниц и фамилии примеров не становятся обязательными.

## Локальные требования

`localRequirements` уточняет утверждение существующей нормы с отдельным источником.
`localAdditions` добавляет самостоятельную локальную норму:

```ts
{
  id: 'local.test-results',
  source: 'Методические указания кафедры, пункт 4',
  explanation: 'Задание требует раздел результатов испытаний',
  rule: {
    // Полная карточка Rule без source, с тем же id.
    // Источник локальной нормы указан выше и не выдаётся за пункт СТУ.
  }
}
```

У новой нормы собственные условия, область, модальность, свойство, утверждение,
исключения и требования к доказательствам. Она сохраняется рядом с исходным СТУ.
Импортированные данные не исполняются. Отсутствие реализации локальной проверки
даёт `unknown`. Профили `stu-2021.1` читаются с обновлением ссылки на каталог;
объект вызывающей стороны не изменяется.

## Критерий 100 % покрытия

Три показателя должны оставаться раздельными:

1. Возможность шаблона представить требование.
2. Полнота переноса каждого обязательства из источника в заполненный каталог.
3. Возможность автоматически проверить требование в конкретном документе.

`assessTraceability()` принимает полный, отдельно проверенный реестр `SourceAtom`,
явные `AtomDecision` и правила. Для нормативного атома требуется решение
`included`, `expert` или `external`, непустой список правил и точное совпадение
локаторов этих правил с атомом. Для экспертного решения обязательна возможность
`manual`; для внешнего — ссылка на внешнюю норму. Определения, примеры и
справочные записи получают самостоятельное решение `context`.

Фрагмент нельзя считать покрытым только потому, что какое-либо правило ссылается
на тот же пункт. Добавление нового атома без отдельного решения снижает показатель.
Пропуск, дубликат, неизвестная ссылка или несовпадение хеша не позволяют подтвердить
100 %. Пустой реестр даёт 0 %, а не 100 %.

**Текущий постраничный `SOURCE_COVERAGE` остаётся старым индексом связности.
Он не является полным проверенным реестром атомарных обязательств. В этой редакции
100 % переноса всего СТУ ещё не подтверждены.** Новые тесты покрывают все 15 тем
аудита, но количество этих тестов не заменяет сверку каждого обязательства.
Для завершения переноса необходимо заполнить и содержательно проверить полный
атомарный реестр, связать с ним все правила и получить пустой `unresolved`.
